# 0031. 列レベルの ER 図はモデルから生成し、仕様書には意図の図だけを描く

- **状態**: 採用
- **日付**: 2026-10-10

## 背景

`4_Database.md` には手書きの Mermaid ER 図があった。ADR 0001 は「ER 図が表す
設計意図は乖離しなかった」と記録したが、図に書かれた**列**は乖離していた。
2026-10 の時点で `llm_usages`・`analysis_inputs`・`parameter_tunings` の
3 テーブル、`users → chats` の関連、派生属性の来歴列、`last_highlight_config`、
`token_version` などが欠けていた。

ADR 0030 で属性に列を加え、DB の構造はさらに読み取りにくくなった。全体を
一目で見られる図は必要だが、手で描けば同じ道をたどる。

## 決定

ER 図を 2 種類に分ける。

- **列レベルの図**は `common/models.py` から生成する（`common/schema_doc.py` が
  `common/schema.md` を書く）。手で決めるのは、各テーブルをどの領域の図に
  載せるかだけである。生成物が古いとき、または領域に属さないテーブルがあるとき、
  `backend/tests/test_schema_doc.py` が落ちる。
- **意図の図**は `4_Database.md` に手で描く。エンティティと関連だけを描き、列は描かない。
  DB の情報が LLM に届く経路のように、モデルからは導けない構造を描く。

生成物は `specification/` ではなく `common/` に置く。両コンテナが共有するのは
`common/` だけで、テストはコンテナ内で走るためである（`common/mcp_tools.json`
と同じ理由、ADR 0027）。

## 根拠

**却下案 A: 手書きの図を保守する.** 乖離はすでに起きた。図を見る人が、
古さに気づけない。

**却下案 B: 外部ツール（ERAlchemy、paracelsus など）で生成する.** 依存が増え、
出力を領域ごとに分けられない。必要なのは SQLAlchemy のメタデータを走査する
100 行程度の処理である。

**却下案 C: 全テーブルを 1 枚の図にする.** 17 テーブル・約 150 列の図は、
描画しても読めない。領域ごとに分け、他の領域のテーブルは列なしの参照先として描く。

**却下案 D: DB に接続して実スキーマから生成する.** マイグレーションを
適用した DB が必要になり、テストで使う SQLite とも食い違う。モデルが正である。

## 帰結

- モデルを変えたら `backend/` で `python -m common.schema_doc` を実行する。
  新しいテーブルは `schema_doc.DOMAINS` のいずれかに加える。
- 列の意味を図に出したいときは、その列に `comment=` を付ける。コメントは
  生成図と DB の両方に現れる。
- `4_Database.md` は列を書かない。列に触れたくなったら、生成図へリンクする。
