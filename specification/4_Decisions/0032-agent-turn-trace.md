# 0032. エージェントのターンを構造化トレースとして記録する

- **状態**: 採用
- **日付**: 2026-10-19
- **関連**: [0022](./0022-evaluator-friction-journal.md)、[0025](./0025-normalized-token-usage.md)

## 背景

会話がうまく進んだかを後から判定するには、ツール呼び出しの結果だけでなく、
その前後で何が起きたかが要る。DB の `tool_executions` と `llm_usages` には
呼び出しと消費量しか残らず、次の情報は stdout のログ行にしかなかった。

- フックの判定（deny / defer / modify）と、判定したフック名・理由
- 各イテレーションでモデルに提示したツールの集合
- `inject_skill_suggestions` が提案した Skill と、実際に `skill_load` された Skill
- continuation（終了直前の再生成要求）と、ターンの中断理由

ログ行は人が読む形式で、ターン単位にまとまっていない。そのため「Skill を提案
したのに読まれなかった」「ガードに拒否された後に自己修正できたか」を機械的に
集計できなかった。

## 決定

1. 1 ターンを、順序付きの構造化イベント列として JSONL に追記する。1 行 = 1 イベント
   で、`turn_id` で同じターンのイベントを束ねる。イベントの種類は `turn_start`、
   `generation`、`model_response`、`tool`、`continuation`、`turn_end` の 6 つである。
2. 出力先は既定で `backend/logs/turns/<日付>.jsonl` とする。`AGENT_TRACE_DIR` で
   変更でき、`AGENT_TRACE=0` で無効にできる。
3. トレースは観測だけを担い、ターンの挙動を変えない。書き込みに失敗しても
   ターンは止めない（フックと同じく fail open）。
4. 本文・引数・結果は長さを切り詰めて記録する。トレースは分析のためのもので、
   会話の復元には DB を使う。
5. 集計は `scripts/analyze_turns.py` が行う。ツール別の成否、拒否したフック、
   Skill の提案と読み込みの一致、イテレーション数、continuation と中断を出す。

## 根拠

DB にテーブルを足す案は、マイグレーションと ER 図の更新が要り、評価のたびに
増える行を本番データと同じ場所に置くことになる。分析は開発者がローカルで行う
ため、追記専用のファイルで足りる。

既存の `audit_turn_summary` フックを拡張する案は、PRE_TOOL の判定やイテレーション
ごとの提示ツールを TURN_END の時点で復元できないため採らなかった。判定が下る
その場所（`engine.py`）でイベントを出す。

OpenTelemetry などの外部基盤は、単一プロセスの研究用アプリには重く、
集計スクリプトで直接読める JSONL のほうが扱いやすい。

## 帰結

- イベントの形は `backend/app/services/llm/trace.py` が持ち、出力は `engine.py`
  からだけ行う。
- トレースは評価ハーネス（ADR 0022）の記録とは独立で、通常の利用でも出力される。
  出力先は gitignore 済みの `logs/` 配下である。
- イベントにフィールドを足すときは、`scripts/analyze_turns.py` が未知のフィールドを
  無視できることを保つ。
