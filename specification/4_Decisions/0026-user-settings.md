# 0026. ユーザー設定: 既定モデルとパスワード変更

- **状態**: 採用
- **日付**: 2026-09-29

## 背景

LLM のモデルはチャットごとに固定するか、サーバーの環境変数で決まる既定に
従うかしかなかった。利用者が普段使うモデルを変えるには、チャットごとに選び直す
必要があった。パスワードを変更する手段もなかった。

JWT はステートレスで、発行済みのトークンは期限まで有効である。パスワードを
変えても、他の端末のセッションは残る。

## 決定

1. `users` に `default_provider` と `default_model` を持たせる。チャットが使う
   モデルは **チャットの固定 > ユーザーの既定 > 環境変数の既定** の順に決まる。
   エージェントのターンとタイトル生成の両方がこの順に従う。
2. 既定モデルは、`GET /chat/providers` がその時点で提供している組み合わせだけを
   受け付ける。プロバイダーとモデルは両方指定するか、両方 `null` にする。
3. `users` に `token_version` を持たせ、JWT に `ver` として埋め込む。
   `ver` が一致しないトークンは拒否する。パスワード変更で版を上げ、変更した
   セッションには新しいトークンを発行する。
4. パスワード変更には現在のパスワードを要求する。新しいパスワードは登録時と
   同じ最小長とする。
5. `/settings` 画面に「Account」「LLM」「Usage」のタブを置く。ヘッダーの
   ユーザー名から開く。

## 根拠

トークンの失効リストを持つ案は、失効したトークンの保存と期限切れの掃除が要る。
ユーザーごとの版番号なら、比較 1 回で「それ以前のトークンすべて」を失効できる。
代わりに、1 つのセッションだけを失効させることはできない。

`ver` のない既存トークンは版 0 とみなす。移行時に全員をログアウトさせずに済む。

既定モデルの検証を保存時だけにしたのは、LM Studio のモデル一覧が実行時に変わる
ためである。保存後に消えたモデルは、そのまま `_create_provider` に渡り、
プロバイダー側のエラーとして見える。設定画面では「unavailable」と表示する。

## 帰結

- 解決順は `engine.resolve_chat_model` の 1 箇所にある。
- 認証は `auth.get_current_user` が `ver` を検査する。トークンを発行する箇所は
  `_issue_token` に集約した。
- ログアウトは従来どおり Cookie を消すだけで、Bearer トークンは失効しない。
