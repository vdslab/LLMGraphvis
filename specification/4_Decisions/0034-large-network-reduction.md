# 0034. 大規模ネットワークでは削減を提案し、選ぶのはユーザーにする

- **状態**: 採用
- **日付**: 2026-10-22

## 背景

ADR 0033 で初期レイアウトは数十秒で終わるようになった。しかし 3,000 ノード級のグラフは、
描くとノードが密集して読めない。媒介中心性や Kamada-Kawai など重い計算は、数分かかる。

削減の道具（`subgraph_largest_component`、`subgraph_k_core`、`subgraph_high_degree_nodes`、
`subgraph_extract_filter`）はすでにあった。足りなかったのは次の 3 つである。

- 削減したら何ノード残るのかを、作る前に知る手段がない。エージェントは具体的な数字で
  選択肢を出せなかった。
- 「大きい」と判定する仕組みがない。ユーザーは「大きい」とは言わないので、
  skill のトリガー（キーワード照合）では手順にたどり着けない。
- 提案の仕方を決めた手順（skill）がない。

## 決定

1. **「大きい」はレイアウトのコストで定義する。** 既定の ForceAtlas2 が下限の反復回数でも
   予算（ADR 0033）を超えるノード数（`fa2_budget_floor_nodes()`）以上を「大きい」とする。
   しきい値は networkx-api の `logic/reduction.py` だけが持つ。`network://{id}/structure`
   リソースが `large` と `large_threshold_nodes` を返し、backend はその値を読むだけにする。
2. **読み取り専用ツール `subgraph_suggest_reduction` を追加する。** 削減候補ごとに、残る
   ノード数・エッジ数、失われるもの、適用に使う既存ツールと引数を返す。何も作らない
   （`layout_suggest_parameters` と同じ形）。適用は名前の挙がったツールを普通に呼ぶ。
   候補は次の 4 種類。
   - 最大連結成分
   - 目標ノード数に収まる最小の k の k-core（ほかの k の大きさも返す）
   - 次数の下限
   - 値の種類が少ないカテゴリ属性のグループごとの大きさ
3. **skill `network-reduction` が提案の手順を持つ。** 提案は 1 回だけにする。
   ネットワーク全体を残す選択肢を必ず含め、`ask_user` で選んでもらう。回答の前には
   抽出しない。
4. **大きいネットワークでは、その skill を毎ターン候補として示す。**
   `inject_skill_suggestions` は表示中のレイアウトの skill を追加しているが、それと同じ
   仕組みで追加する。`large` の値は、毎ターンの文脈要約（`build_turn_context`）と同じ
   取得から得る。MCP への往復は増えない。
5. アップロード時の概要に、大きいこととその相談の仕方を一行で書く（LLM を使わない）。

## 根拠

- **自動で削減しない**：削減すると、以後のすべての指標が部分グラフについての値になる。
  何を捨ててよいかは分析の目的による（孤立ノードこそ見たい場合もある）。
  これは「分析範囲を変えるときだけ抽出する」という既存の方針（`subgraph-workflow`）と
  同じ考えである。
- **しきい値をレイアウトのコストに結び付ける**：見た目の密集度には一つの基準がない。
  一方、このアプリで「大きいと困る」が最初に表に出るのはレイアウト時間であり、
  ADR 0033 の予算とそのまま対応する。
- **候補を事前に計測する**：「k-core にしますか？」では選べない。
  「1,343 ノードが残ります」なら選べる。

却下した代替案:

- **アップロード時に自動で最大連結成分に絞る**：ユーザーの知らないうちに分析範囲が変わる。
- **しきい値を backend にも持つ**：二か所の数値がずれると、文脈要約とツール結果が
  食い違う。
- **毎ターン `structure` を読む専用のフックを足す**：文脈要約と同じリソースを
  二度取得することになる。

## 帰結

- `structure` リソースの `large` / `large_threshold_nodes` が、大きさの判定の唯一の出どころ。
  ADR 0033 の定数を変えると、しきい値も変わる。
- `subgraph_largest_component` は、有向グラフでは弱連結成分を使うようにした
  （候補として示す以上、有向グラフで失敗してはいけない）。
- 実装：`networkx-api/app/logic/reduction.py`、`mcp/tools/subgraph/suggest.py`、
  `backend/app/services/llm/context.py`（`build_turn_context`）、
  `skills/registry.py`（`REDUCTION_SKILL`）、`skills/definitions/network-reduction.md`。
