# 0001. 仕様書のスコープをコードから導出できないものに限定する

- **状態**: 採用
- **日付**: 2026-08-20

## 背景

`specification/` は 2025年11月に「レイヤード・ドキュメンテーション」として整備され、11文書・約2,400行に育った。しかし 2026年8月時点で、大半が実装と乖離していた。

乖離の分布には明確な偏りがあった。

**乖離していた記述:**

- エンドポイント一覧（`POST /auth/logout`、`GET /chat/providers`、`PATCH /chat/{id}` が欠落）
- MCP ツール名（`calculate_centrality` は 7 ツールに分割済み、`generate_visualization` は `visualization_generate` に改名済み。旧名が全文書に残存）
- DDL の列定義（`tool_executions` テーブルが丸ごと欠落、存在しない `networks.graphml_content` を記載）
- フロントエンドのコンポーネント一覧、SSE イベント一覧（4件記載・実際は11件）
- 時点計測値（プロンプト文字数の削減率）
- セットアップ手順（存在しないリポジトリ、誤ったポート、誤った環境ファイル名）

**乖離していなかった記述:**

- C4 コンテキスト図・コンテナ図
- 認証フローのシーケンス図
- ER 図が表す設計意図（属性のサブタイプ階層、派生属性のキャッシュ方針）
- Agent Policy（最小主義、ユーザー主権、検証優先）とその論拠

さらに示唆的なのは、2026年7月に更新された 2 文書（`1_Backend.md`、`3_NetworkXAPI.md`）だけが正確さを保っていた点である。この 2 文書は明示的に「実装の docstring と `Field(description=...)` を唯一の情報源とする」方針を採り、列挙の複製をやめていた。

## 決定

仕様書には **コードから機械的に導出できない情報のみ** を書く。

- **書く**: 設計判断と根拠、却下した代替案、不変条件とその理由、契約、意図を表す図、研究上の設計原則
- **書かない**: エンドポイント表、ツール名一覧、DDL、コンポーネント一覧、パラメータ表、時点計測値、セットアップ手順

判定基準は「この記述はコードから機械的に導出できるか？」であり、Yes ならコードを指す。

仕様駆動開発は **新機能とアーキテクチャ変更のみ** に適用する。実装前に本ディレクトリへ ADR を書き、実装後に該当する `2_Technical_Details/` 文書へ根拠を反映する。既存実装の遡及的な仕様化は行わない。

この決定に伴い以下を実施した。

- `1_Quick_Start/` を削除（`QUICKSTART.md` と重複し、最も乖離が激しかった）
- `3_Developer_Guide/` を削除（`AGENTS.md` が置き換える）
- `2_Technical_Details/` の各文書から列挙を除去し、旧ツール名を現行名に置換
- ルートに `AGENTS.md` を新設し、`CLAUDE.md` と `.agent/rules/` をそのポインタにした

## 根拠

**却下案 A: フル仕様駆動開発への移行.** 全機能を仕様から駆動する。既存の 52 MCP ツール・4 LLM プロバイダ・hooks/skills 機構を遡及的に仕様化するコストが大きく、一人開発では仕様と実装の二重メンテナンスに陥る蓋然性が高い。乖離の原因は「仕様が足りない」ことではなく「同じ事実が二箇所にある」ことなので、仕様を増やしても解決しない。

**却下案 B: 仕様書の廃止.** `specification/` をアーカイブし、コードと `AGENTS.md` のみを情報源とする。運用は最も軽いが、設計判断の根拠がリポジトリから失われる。本プロジェクトは修士論文であり、「なぜこの設計なのか」の記録そのものが成果物の一部である。

**却下案 C: 現状凍結.** 各文書に「YYYY-MM 時点のスナップショット」と明記して凍結する。作業量はゼロだが、`AGENTS.md` が仕様書を権威として参照できなくなり、実質的に案 B と同じになる。

採用案は、乖離の実測分布が示した境界線をそのまま規約にしたものである。腐った記述と腐らなかった記述を分けていたのは文書の新しさではなく、**その事実がコードに二重に存在していたかどうか**だった。

## 帰結

- 仕様書はコード変更に追従する義務を負わない。コードを変えても、設計判断が変わらない限り仕様書は変わらない。これが陳腐化しない条件である。
- 逆に、**設計判断が変わったときは仕様書の更新が必須**になる。ADR の追加または既存文書の根拠部分の書き換えを伴わない設計変更は、レビューで差し戻す対象とする。
- 「このツールは何をするか」を知りたい読者は、仕様書ではなく docstring と `Field(description=...)` を読む。したがってツールの docstring はプロンプト表面であると同時にドキュメントでもあり、その品質要求は従来より高い（`AGENTS.md` の "Where behaviour lives" 参照）。
- `AGENTS.md` 自身も同じ規約に従う。ツール数などの導出可能な数値は記載しない。
- 関連する実装: `networkx-api/app/mcp/tools/`（docstring）、`backend/app/services/llm/prompts.py`（常時ポリシー）、`backend/app/services/llm/skills/definitions/`（手順書）。
