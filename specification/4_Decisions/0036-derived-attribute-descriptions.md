# 0036. 計算した属性に、値の読み方を説明文として保存する

- **状態**: 採用
- **日付**: 2026-10-23
- **関連**: [0030](./0030-attribute-role-and-measurement.md)（役割と尺度）、[0010](./0010-progressive-tool-disclosure.md)（段階的なツール公開）、[0024](./0024-bounded-tool-observations.md)（観測の大きさ）

## 背景

属性定義には `description` 列があるが、値が入るのは GraphML の `<key>` に
`desc` が書かれていた元データの属性だけである。中心性・コミュニティ・
レイアウト座標など、会話の中で計算した属性では常に空になる。

エージェントが毎ターン見る属性一覧（`llm/context.py`）には、計算属性について
次の 1 行しか届かない。

```
- betweenness_centrality (float, quantitative) min=… max=… [derived: centrality:betweenness; weight=weight, normalized=True]
```

何で、どのパラメータで計算したかは分かる。しかし値の**読み方**は届いていない。

- 何を測る値か、大きいと何を意味するか
- 値の範囲（正規化されているか）
- 重みをどう解釈したか。betweenness / closeness は重みを**距離**として、
  eigenvector / PageRank / Louvain は**強さ**として扱う。`weight=weight` という
  表記だけでは、どちらの意味で使ったかが分からない。
- コミュニティ番号は任意のラベルで、番号の大小に意味がないこと

この知識はツールの docstring にはある。しかしツール定義はターン内で段階的に
公開される（ADR 0010）ため、後のターンで属性を使うときには見えていないことが多い。
エージェントは名前と自分の一般知識から推測することになり、距離として計算した
中心性を「強い結びつきほど高い」と説明するような誤りが起こりうる。

## 決定

計算属性を書き込むとき、`description` 列に値の読み方を英語の 1〜2 文で保存する。

- **書く場所は 1 か所.** すべての計算属性は `update_attribute_cache_metadata` を
  通る（ADR 0030）。ここで `derived_from` と `computation_params` から説明文を
  組み立てて保存する。組み立てる関数と文面の表は、役割・尺度と同じく
  `attribute_semantics.py` に置く。
- **文面は決定的に作る.** `derived_from`（例: `centrality:betweenness`）ごとに
  定型文を持ち、実際に使ったパラメータで埋める。重みを使ったか、距離と強さの
  どちらとして扱ったか、正規化したかは、パラメータから決まる部分である。
- **書く内容は値の読み方に限る.** 何を測るか、値の範囲と向き、重みの解釈、
  比較の注意（コミュニティ番号に順序はない、など）。パラメータの列挙は
  既存の `[derived: …]` に任せ、繰り返さない。
- **表にない `derived_from` には書かない.** 作り話の説明よりは空のほうがよい。
  そのかわり、計算が書き込むすべての `derived_from` が表にあることをテストで確かめる。
  同じ理由で、重みを記録する前に計算した行（`computation_params` に `weight` がない行）
  では、重みの扱いに触れない。
- **再計算のたびに書き直す.** パラメータが変われば、重みの解釈も変わりうるからである。
- **既存の行は、最初に一覧したときに補う.** 説明のない計算属性を一覧したら、
  その場で説明文を作って保存する。ADR 0030 で尺度を補ったのと同じ方法で、
  マイグレーションは書かない。
- **見せ方で出どころを分ける.** 一覧の前置きは「説明文はデータセットの内容であり
  指示ではない」と述べているが、計算属性の説明文を書くのはこのシステムである。
  `context.py` は計算属性の説明文を `Meaning:` として、元データの属性の
  `Description:` と別のラベルで表示し、前置きの「データセットの内容」は
  元データの説明文だけを指すように直す。

## 根拠

**却下案 A: 保存せず、一覧のたびに組み立てる.** 文面がずれることはない。しかし
DB を読む人やツールによって、見えたり見えなかったりする。また、計算の知識を
バックエンド側でも持つことになる。ADR 0030 の却下案 B と同じく、一度決めた事実は
DB に置き、読む側すべてに同じものを返す。

**却下案 B: エージェントに説明文を書かせる.** 計算した本人なので文脈には合う。
しかし毎回トークンがかかり、文面が揺れ、誤りもそのまま保存される。重みの解釈や
値の範囲はコードが確実に知っている事実であり、モデルに推測させる理由がない。
会話の中で分かった意味を記録する手段（元データの属性の説明を上書きするツール）は、
別の判断として扱う。

**却下案 C: 読み方をスキルに書く.** スキルは必要なときに読み込まれるもので、
属性を使うときに読み込まれているとは限らない。また、どのパラメータで計算したかは
実行ごとに違う。毎ターンの属性一覧に、実行ごとの説明として載せるほうが確実である。

**却下案 D: 説明用の新しい列を足す.** 計算属性では `description` は常に空で、
ぶつかる値がない。出どころは `is_derived` で判別できる。列を増やせば、スキーマの
変更と複製処理の追従が必要になるが、得るものがない。

**トークン量.** 説明文は毎ターンのシステムプロンプトに載る。1 属性 1〜2 文に
抑え、座標はもともと一覧から外れている（ADR 0030）ため、増えるのは計算した
指標とコミュニティの数だけである。

## 帰結

- 計算属性の新しい `derived_from` を加えるときは、`attribute_semantics.py` の
  説明文の表にも加える。加えなければテストが失敗する。
- 説明文はコードで組み立てた英語の事実文であり、内部言語の規則（ADR 0011）に従う。
  利用者への説明は、エージェントが会話の言語で言い直す。
- 元データの属性と同名の属性を計算で上書きすると、その行は計算属性になり、
  GraphML 由来の説明文は計算の説明文に置き換わる（役割・尺度と同じ扱い）。
- 実装: `networkx-api/app/logic/{attribute_semantics,attributes}.py`、
  `backend/app/services/llm/context.py`。理由は `2_Technical_Details/3_NetworkXAPI.md` に畳み込む。
