# 0025. トークン使用量をプロバイダー共通の意味で記録する

- **状態**: 採用
- **日付**: 2026-09-29

## 背景

チャットヘッダーのトークン数とコストを点検したところ、次の誤りがあった。

- **Gemini の思考トークンが出力に入っていなかった。** `candidates_token_count` には
  思考が含まれず、思考は `thoughts_token_count` に別に報告される。課金上は出力なので、
  Gemini 3 系では出力とコストを大きく過少に表示していた。
- **「入力」の意味がプロバイダーごとに違った。** Gemini と OpenAI の入力はキャッシュ
  読込を含むが、Anthropic の `input_tokens` は含まない。一方でキャッシュ書込は
  Anthropic の入力に足していた。合計を比べても意味がなかった。
- **Anthropic のキャッシュ書込を通常の入力単価で計算していた。** 実際は 1.25 倍である。
- **記録から漏れる呼び出しがあった。** チャットタイトル生成の呼び出しは一切記録
  されず、エラーや空応答で終わったターンは消費しても保存されなかった。画面は
  クライアント側で足し込んでいたため、再読み込みすると数値が減った。
- `iteration_count` は常に 1 で、ターンの内訳（ReAct の何回目がどれだけ使ったか）は
  見られなかった。

## 決定

1. `UsageData` の意味を 1 つに定める。**入力はプロンプト全量**（キャッシュ読込と
   書込を含む）、**出力は生成全量**（思考を含む）。キャッシュ読込・書込・思考は
   その内数として別に持つ。各プロバイダーのアダプターがこの意味へ変換する。
2. コストは全プロバイダー共通の 1 つの式で計算する。単価表にないモデルのコストは
   `None`（不明）とし、0 と区別する。LM Studio は 0 とする。
3. `llm_usages` に 1 行 = 1 つの LLM タスク（エージェントのターン、チャットタイトル）
   を記録する。`purpose` で種類を、`calls` で generate() 呼び出しごとの内訳を持つ。
   `chat_id` と `user_id` を持たせ、メッセージが残らないタスクも記録する。
4. 画面の数値はバックエンドに保存された値だけを正とする。進行中のターンだけ SSE の
   累計を上に重ね、ターンの終了・エラー・タイトル生成の後に保存値を取り直す。
5. 詳細はヘッダーのバッジから開くポップオーバー（チャット単位、ターンごとの内訳）
   と、設定画面の「Usage」タブ（ユーザー単位、モデル別・チャット別・日別）で見る。

## 根拠

プロバイダーごとに式を変える案（従来の `PROVIDERS_WITH_CACHED_IN_INPUT`）は、
意味の違いを計算箇所へ持ち込むので、表示・集計の全箇所が同じ分岐を知る必要がある。
変換をアダプターの 1 箇所に閉じ込めれば、以降は単純な足し算で済む。

クライアント側で足し込む案は、保存に失敗したターンや、後から走るタイトル生成を
反映できない。保存値を取り直せば、再読み込み前後で数値が一致する。

呼び出しごとの行を別テーブルに持つ案もあったが、ターン単位の集計が主な用途で、
内訳は表示にしか使わないため JSON 列で足りる。

## 帰結

- 変換は `providers/*_provider.py`・`google_genai.usage_from_metadata`、式は
  `pricing.estimate_cost_usd`、保存は `llm/usage.record_usage`、集計は
  `services/usage_report.py` にある。
- 新しいプロバイダーを足すときは、`UsageData` の docstring の意味に合わせて変換する。
- 移行前の行は旧来の意味のまま残る。思考トークンやキャッシュ書込は後から取得
  できないため、再計算しない。
- API: `GET /chat/{id}/usage`、`GET /users/me/usage`。
