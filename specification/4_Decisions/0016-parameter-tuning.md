# 0016. パラメーター調整は言葉を主とし、上級者向けパネルと状態を共有する

- **状態**: 採用
- **日付**: 2026-09-17
- **関連**: [0004](./0004-conversation-inputs.md)（入力要求）、[0010](./0010-progressive-tool-disclosure.md)（段階的公開）、[0014](./0014-activation-survives-a-question.md)（回答をまたぐ公開状態）

## 背景

コミュニティ検出の `resolution` や ForceAtlas2 の `scaling_ratio` のように、結果の見え方が
パラメーターで大きく変わる処理がある。ユーザーはそれを「もう少し細かく」「さっきの方が
よかった」と言葉で調整したいが、エージェントは現在値・妥当な範囲・直前の値を持っておらず、
相対表現を数値に落とす根拠がなかった。

`ask_user` の入力要求（0004）は slider / number を持つが、質問はターン境界であり、
1回試すごとに LLM 往復が要る。ツール説明も「画面上の調整にはフォームを使わない」と
誘導しており、試行錯誤には向かない。

## 決定

**調整セッション**（`parameter_tunings` 行）を導入する。1つのセッションは、
現在の表示に対して実際に成功したツール列（パイプライン）とその引数、LLM が選んだ
1–4 個の調整フィールド、現在値・推奨値・変更履歴を持つ。

1. **言葉が本線**。エージェントは `apply_parameter_tuning` で値を変える。相対表現は
   セッションの現在値・範囲・step・両端ラベル・履歴から数値化し、前後の値を報告する。
   フィールド外の引数も、パイプライン内のツールのスキーマにあれば言葉で変えられる。
2. **パネルは可視化に詳しいユーザー向けの補助**。`offer_parameter_tuning` で会話の結果に
   添える。実パラメーター名・ツール名・範囲・step・スキーマの説明を出し、初心者向け
   プリセットは持たない。両端ラベルは方向を示す補助として残す。
3. **2経路は1つの状態を共有する**。パネルの「適用」とエージェントの呼出しは同じ
   `tuning.apply()` を通り、パネルは再取得で言葉の適用に追従する。パネルの「適用」は
   LLM を介さずパイプラインを再実行して再描画する。
4. **エージェントは常に現在値を知る**。active なセッションがあるターンでは、TURN_START で
   現在値・推奨値・履歴・未報告のパネル適用を文脈に入れ、`apply_parameter_tuning` を公開する。
5. **結果が敏感なら一度だけ提案を促す**。コミュニティ検出や力学レイアウトを描いたのに
   パネルを付けずに終えた場合、NO_TOOL_CALLS フックが1回だけ付与を求める。
6. **推奨値は自動適用しない**。LLM の目安はパネルの初期位置と理由として示すだけで、
   キャンバスは変えない。

`ask_user` とは別ツール・別テーブルにする。

## 根拠

`ask_user` に相乗りしなかったのは、質問が「実行バリア」「pending な質問への自由記述は回答」
という不変条件を持つため。調整パネルはターンを止めず、無視されても構わない。同じ行で
扱うと、パネルが出ているだけで次の発話が回答として消費される。

ベース引数をモデルに書かせず、実行済みの呼び出し（同じターンなら PRE_TOOL の正規化・修正後、
前のターンなら保存された引数に `network_id` を補ったもの）から取るのは、
ガードを通過して実際に動いた呼出しだけを再実行対象にするため。パネルの「適用」で
PRE_TOOL フックを通さないのはこの前提に依る。変わるのはスキーマ範囲内の値だけで、
最終的な型・範囲の判定は MCP 側の検証が行う。

再実行できるツールは `analysis_` / `layout_` / `visualization_` に限り、`subgraph_*` と
`visualization_switch_network` を除く。前者は適用のたびに新しいネットワークを作り、
後者は見ている対象そのものを変えてしまい、「同じ結果のパラメーター違い」にならない。

効果の説明をモデルに書かせず、ツールスキーマの `description` をサーバーで引くのは、
`Field(description=...)` を単一の事実源にするため（0001）。

推奨値を自動適用しないのは User Agency のため。エージェントが明らかに良いと判断した値は、
パネルを出す前にその値で実行しておけばよく、提示と適用を混ぜる必要がない。

却下した代替案:
- **パネルを主にする**: 対象ユーザーの主操作は会話であり、パネルは数値を直接扱える人の
  近道に留める。
- **パイプライン全パラメーターをパネルに出す**: 行数が増えて比較の焦点がぼやける。
  出さない引数も言葉で変えられるため、LLM の選定で足りる。
- **会話全体で公開集合を持ち越す**（0014 と同じ理由で却下）: active なセッションがあるときに
  `apply_parameter_tuning` だけを足す。

## 帰結

- `parameter_tunings` は chat と network に結びつく。active なセッションは network ごとに
  最大1つで、新しいパネルは古いものを `superseded` にする。network が変わると `expired` と
  して扱う。
- パネルの「適用」はエージェントのターン外で描画を変える。モデルがそれを知る経路は
  TURN_START の文脈注入（`reported_at` 以降の変更）だけである。
- `offer_parameter_tuning` はこのターンの実行記録（`turn_state["executed_calls"]`）と、
  このチャットの保存済みツール実行を参照する。「さっきの結果を調整できるようにして」を
  次のターンで頼めるようにするためである。保存済み引数に `network_id` が無い呼び出しは
  現在の表示のものとみなす。
- 描画済みの結果について調整を頼む発話（`parameter-tuning` スキルのトリガーに一致）では、
  そのターンの開始時に `offer_parameter_tuning` と元のパイプラインのツールを公開し、
  パイプラインをシステムプロンプトに示す。公開しないと小さなモデルは `ask_user` の
  メニューに流れた。
- 提案の促しはスキルの記述だけでは足りなかった（ローカルモデルが締めの一文を
  `ask_user` のメニューに変えた）。促しは `nudge_choice_ui` より先に1ターン1回だけ行う。
- 実装: `backend/app/services/llm/tuning.py`、`hooks/builtin/tuning.py`、
  `hooks/builtin/context_blocks.py`、`skills/definitions/parameter-tuning.md`、
  `frontend/src/components/chat/ParameterTuning.jsx`。
