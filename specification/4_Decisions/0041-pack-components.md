# 0041. 複数の連結成分からなるグラフは、成分ごとに配置して詰める

- **状態**: 採用
- **日付**: 2026-10-23
- **関連**: [0017](./0017-layout-quality-metrics.md), [0033](./0033-forceatlas2-iteration-budget.md), [0040](./0040-edge-backbone.md)

## 背景

エッジのバックボーン（ADR 0040）を取ると、大きなネットワークは多数の連結成分に
分かれる。シラバス類似度ネットワークの k=2 バックボーン（3383 ノード、4659 エッジ、
194 成分、最大成分 1939 ノード）では次のようになった。

- ForceAtlas2 は反復を予算で 50 に切られ（ADR 0033）、一様な円盤になる。
- spring は自動調整で `method='energy'`、gravity 3、200 反復になり、約 80 秒かかる。
  最大成分は一つの塊に潰れ、小さい成分は最大成分の枝の間に紛れて、別の集まりとして
  見えない。

Gephi などの見慣れた描画では、最大成分が中央にあり、小さい成分がその周りに
一つずつ見分けられる形で並ぶ。全体を一つの力学系で解くと、成分同士の位置は
gravity と斥力の釣り合いでしか決まらないので、この形にならない。

## 決定

1. spring に引数 `pack_components` を加える。真のとき、各連結成分を別々に
   spring で配置し、辺の長さの中央値で尺度を揃えてから、大きい順に
   「中心に最も近い空き位置」へ置く。各成分は細い凹みを埋めた輪郭ごと場所を取るので、
   小さい成分が最大成分の枝の間に入り込まず、成分同士が噛み合って辺が交差することもない。
2. 複数の成分を持つグラフでは `pack_components` を既定で真にする。この場合、
   以前の `method='energy'` と gravity による調整は行わない（各成分は連結なので
   gravity で引き留めるものがない）。`pos` か `init_from_layout` を渡したときは
   開始位置が配置を決めるので詰めない。
3. 反復回数は最大成分の大きさで決め、N² × 反復回数の予算で上限を設ける（ADR 0033 と同じ考え方）。
4. energy 法で解く成分（500 ノード以上）は、短い実行と、それを上限まで続けた実行の
   両方を `layout_quality` で採点し、良い方を採る。
5. `pack_components` は networkx の引数ではなく、アプリが消費する引数である。
   `@register` の `app_params` に宣言し、許可リスト・キャッシュキー・
   「Effective parameters」には通常の引数と同じく載せる。
6. ForceAtlas2 とアップロード時の初期レイアウトは変えない。

## 根拠

`layout_quality.evaluate` の総合点（小さいほど良い）で測った。時間は開発機のホスト上。

| グラフ | 以前の spring | 詰める spring |
|---|---|---|
| 上記バックボーン（194 成分） | 4.42 / 47 秒 | 2.94 / 16 秒（Docker 上 27 秒） |
| シラバス全体（3393 ノード、262 成分） | 4.09 / 48 秒 | 3.05 / 16 秒 |
| concert（1144 ノード、15 成分、平均次数 15） | 4.11 / 23 秒 | 4.03 / 16 秒 |
| 古典グラフ 4 つ＋孤立ノード 10（seed 5 種の平均） | 0.71 | 0.72 |
| ランダムな 25 成分＋孤立ノード 20（seed 5 種の平均） | 0.68 | 0.63 |

古典グラフの組では差が seed によるばらつき（0.66〜0.79）の範囲に収まり、どちらも
問題の指摘はない。

採った数値（成分の間隔は辺の長さで 2、輪郭を埋める半径は各成分の半径の 0.2 倍）は
コードの定数に置き、その根拠をコメントに残した。

反復回数を採点で選ぶ理由：バックボーンの最大成分は 50 反復で 3.0、100 反復で 3.9、
500 反復で 4.2 だった。収束させると帯状の部分が伸び切り、密な中心が潰れて
外側の帯に描画範囲を取られる。一方 concert・BA・Watts-Strogatz・格子グラフでは、
反復を増やすほど良くなった（concert の最大成分は 50 反復で 5.5、500 反復で 5.2）。
直径 / √N や次数 2 の鎖の長さでは二つを見分けられなかった（格子は直径が長いが
収束させる方が良く、バックボーンの帯は次数 2 の鎖ではない）。そのため
構造から推測せず、描画を測って選ぶ。

却下した代替案:

- **成分の間隔を最近傍距離で測る**：concert は良くなる（3.14）が、バックボーンでは
  小さい成分同士が詰まりすぎ、帯のように並んで一つずつ見分けられなくなった。
- **成分のノード単位で隙間に詰める（輪郭を取らない）**：総合点は最良（2.3）だが、
  小さい成分が最大成分の枝の間に入り、全体が一様な円盤に見えた。目的の形にならない。
- **同心円状に並べる**：外側の環が長くなり、最大成分に割ける面積が減った（4.0）。
- **50 反復ごとに採点して悪化したら止める**：concert では 100 反復で一度悪化してから
  良くなるため、早く止まりすぎた。
- **ForceAtlas2 も成分ごとに詰める**：3.87（詰めない場合 3.89）で改善しない。
  ForceAtlas2 では最大成分そのものの配置が支配的である。

## 帰結

- 複数成分のグラフで spring を呼ぶと、既定で成分ごとに配置される。成分の相対位置は
  力学で決まるのではなく、大きい順の配置規則で決まる。
- `k` はグラフ全体に対する値として扱い、各成分には大きさに応じて換算して渡す。
- 各成分はグラフのノード順で組み立てる。部分グラフのビューは集合の順に反復し、
  文字列の集合の順はプロセスごとに変わるため、同じ seed でも配置が変わってしまう。
- `iterations` は、energy 法で解く大きい成分では上限になる（短い実行の方が良ければそこで止める）。
  ツールの説明と自動調整の注記にそう書く。
- 実装: `networkx-api/app/logic/layouts/components.py`（配置と詰め込み）、
  `force_directed.py` の `tune_spring` と `spring`、`base.py` の `app_params`。
