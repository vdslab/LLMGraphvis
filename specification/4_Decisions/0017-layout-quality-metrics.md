# 0017. レイアウトは描画結果を数値で評価し、パラメーターの数値はコードだけが持つ

- **状態**: 採用
- **日付**: 2026-09-18
- **関連**: [0001](./0001-documentation-scope.md)（文書の置き場所）、[0010](./0010-progressive-tool-disclosure.md)（段階的公開）、[0016](./0016-parameter-tuning.md)（パラメーター調整）

## 背景

エージェントは自分が描いた図を見られない。`visualization_generate` の結果は
LLM には `{rendered, node_count, link_count, legend}` に縮約され、座標は届かない。
画像で渡すとトークン量が大きく、会話のたびに積み上がる。

レイアウトのパラメーターは `tune_*` の固定ルール（ノード数の段階・平均次数）だけで決まり、
連結成分の数、孤立ノード、エッジ重みの大きさ、描いた結果は反映されていなかった。

エッジ重みは「強さ／距離」の扱いこそ正しかったが、値がそのまま networkx に渡っていた。
ForceAtlas2 と spring は重みを引力に掛けるため、同じデータでも単位が変わると図が変わる
（les_miserables で重みを10倍にすると、ノードの重なり率が 5% → 21%）。

skill `layout-tuning` には既定値・範囲・パラメーターの意味が書かれ、ツールの説明文と
二重になっていた。二重の記述はどちらかが古くなる。

## 決定

1. **描画結果を数値で評価する。** 評価はレンダラーと同じ座標変換
   （x, y を独立に [-1000, 1000] へ）と、実際のノード半径 `sqrt(size*10/π)` の上で行う。
   `normalize_like_renderer` を唯一の変換とし、レンダラーもこれを使う。
   指標は軽量なものに限る: ノードの重なり、エッジ交差（大規模では標本推定）、
   エッジ長のばらつき、外れ値による中心部の縮み、縦横比の歪み、空間の使い方。
   `visualization_generate` の結果に `layout_quality` として添え、LLM に毎回届ける。
2. **パラメーターの数値はコードだけが持つ。** 既定値・推奨範囲・閾値・刻みは
   各レイアウトの `@register`（`tune` と `knobs`）と `layout_quality.py` にだけ置く。
   パラメーターの意味と効く方向は `Field(description=...)` に書く。skill は数値を書かず、
   調整の順序や相互作用といった戦略と手順だけを書く。
3. **初期値はグラフの特徴から決め、理由を返す。** `GraphProfile`（規模・密度・連結成分・
   孤立ノード・次数のばらつき・重みの統計・平面性・二部性・森か）から `tune` が値を決め、
   どのルールが効いたかを注記としてツール結果に含める。
4. **強さとしての重みは中央値で割ってから networkx に渡す。** 図に効くのは重みの比だけに
   なる。DB には元の値が残り、注記で正規化したことを伝える。
5. **候補探索は読み取り専用のツールにする。** `layout_suggest_parameters` は検出した問題に
   効く `knobs` を動かして候補を採点し、完全な引数とともに返す。保存も描画もしない。
   適用は常に実際の `layout_*` ツールを呼ぶ。
6. **skill は共通とアルゴリズム別の二層にする。** 共通の `layout` は二段階の不変条件、
   アルゴリズムの選び方（`layout_profile`）、重みの読み方、指標の読み方、改善ループを持つ。
   アルゴリズム別の skill（`layout-<登録名>`）は、相互作用する調整パラメーター（`knobs`）か
   事前の手順を持つものにだけ作る。分割属性や起点を選ぶ手順が共通の
   bipartite / multipartite / shell / bfs は `layout-partitioned` にまとめる。
   表示中のアルゴリズムの skill は、`layout` が候補に出たターンで一緒に候補に出す。

## 根拠

画像ではなく数値にしたのは、トークン量に加えて、描画が解像度に依存しないため。
フロントエンドは正規化座標の範囲に viewBox を合わせ、ノード半径も同じ単位で描く。
したがって正規化後の座標とノードサイズから計算した重なりや交差は、画面の大きさに
関係なくユーザーが見ているものと一致する。

指標を軽量なものに限ったのは、描画のたびに計算するため。stress のように全点対最短路を
要する指標は、規模の大きいネットワークで描画を遅くする。

候補探索を読み取り専用にしたのは、実行済みツールの記録を正しく保つため。探索ツールが
座標を保存すると、パネルの再実行（0016）が元にするパイプラインにレイアウトの呼出しが残らず、
「どの引数で描かれているか」が失われる。実レイアウトの呼出しを1回余分に行う費用は、
同じ seed で決定的に再現できるため小さい。

重みを中央値で割るのは、強さとしての重みに意味があるのは比だけだから。
平均ではなく中央値にしたのは、一部の極端に重いエッジに全体が引きずられないため。

アルゴリズム別の skill を全アルゴリズムに作らなかったのは、circular や random のように
戦略が無いものは skill にしても説明文の重複にしかならず、索引行を増やすだけだから。
逆に共通 skill 一本では、ForceAtlas2 の `scaling_ratio` と `gravity` のように
相互作用するパラメーターの戦略が、使わないアルゴリズムの分まで毎回読み込まれる。

却下した代替案:
- **スクリーンショットを LLM に渡す**: トークン量が大きく、小さなモデルでは読み取りが不安定。
- **探索ツールが最良の座標を保存する**: 上記の理由でパイプラインの記録が壊れる。
- **推奨範囲を skill に表で持つ**（従来）: コードの既定値と食い違っても検出できない。

## 帰結

- `normalize_like_renderer` はレンダラーと評価の共通の変換であり、片方だけを変えてはいけない。
- `LayoutSpec` は `knobs` を持つ。調整できるアルゴリズムを増やすときは `knobs` を宣言し、
  必要なら `layout-<登録名>` の skill を足す。`layout.py` と探索はアルゴリズム名で分岐しない。
- skill に書くパラメーター名は、そのアルゴリズムの `params` に存在しなければならない
  （バックエンドのテストで検査する）。
- 描画後の4択（おまかせ／候補から選ぶ／自分で調整／このまま）は、この決定の上に別途設計する。
- 実装: `networkx-api/app/logic/layout_quality.py`、`logic/layout_optimizer.py`、
  `logic/layouts/`（`GraphProfile`、`tune`、`knobs`、重みの正規化）、
  `mcp/tools/layout/`（`layout_profile`、`layout_suggest_parameters`）、
  `mcp/tools/visualization/state.py`、`backend/app/services/llm/skills/definitions/layout*.md`、
  `hooks/builtin/context_blocks.py`、`networkx-api/scripts/benchmark_layout_quality.py`。
