## 1\. システム概要

本システムは、ユーザーがアップロードしたネットワーク（グラフ）データを、LLM（大規模言語モデル）との対話形式で可視化・分析するためのWebアプリケーションである。

ユーザーは「友達が多い人を大きく表示して」といった曖昧な自然言語や、「次数中心性をノードサイズに割り当てて」といった厳密な指示により、グラフのレイアウト、ノードのサイズや色などをインタラクティブに変更できる。

## 2\. アーキテクチャの基本方針

- **厳格な役割分離**: フロントエンドは描画とユーザー入出力のみを担当する。一切のデータ計算（レイアウト、指標）、LLMとの通信、認証処理は行わない。
- **バックエンド集中処理**: すべてのビジネスロジック、データ処理、LLM連携、認証はバックエンドで完結させる。
- **ステートフルな可視化**: バックエンドは、ユーザー（プロジェクト）ごとに現在の可視化設定（例：ノードサイズ＝次数中心性）を状態（ステート）として管理する。
- **計算結果の永続化**: 一度計算したネットワーク指標（中心性など）やレイアウト座標はデータベースに永続化し、再計算のコストを削減する。

## 3\. コンポーネント定義と処理フロー

システムは大きく「フロントエンド」と「バックエンド」に分かれ、バックエンドはさらに複数のマイクロサービス（またはモジュール）に分割される。

### 3.1. フロントエンド (Client)

- **責務**:
  - ユーザーインターフェース (UI) の提供（チャット画面、可視化描画エリア）。
  - ユーザー認証（ログイン/ログアウト）のインターフェース。
  - グラフデータ（CSV, JSONなど）のアップロード。
  - チャットメッセージの入力と送信。
  - バックエンドから受信した描画データ（JSON）に基づくグラフの描画・更新（例: D3.js, WebGL使用）。
- **入出力**:
  - **入力 (ユーザー操作)**: テキストメッセージ、ファイル。
  - **出力 (バックエンドへの送信)**: APIリクエスト (HTTP)、チャットメッセージ (WebSocket)。
  - **入力 (バックエンドからの受信)**: 描画用JSONデータ、チャット応答テキスト (WebSocket)。
- **禁止事項**:
  - LLM APIとの直接通信。
  - ネットワーク指標（中心性、レイアウト）の計算。
  - 認証ロジックの実装。

---

### 3.2. バックエンド (Backend)

バックエンドは、以下のコンポーネント群で構成される。

#### A. APIゲートウェイ (API Gateway)

- **責務**:
  - フロントエンドからのすべてのリクエスト（HTTPおよびWebSocket）の単一窓口。
  - リクエストの認証（**\[B\] 認証サービス**と連携）。
  - リクエスト内容に基づき、適切な内部サービス（主に\*\*\[C\] チャット/LLMサービス\*\*）に処理をルーティングする。
- **データの流れ**:
  - フロントエンド \$\\leftrightarrow\$ API Gateway \$\\leftrightarrow\$ (各種内部サービス)

#### B. 認証サービス (Auth Service)

- **責務**:
  - ユーザー登録、ログイン、ログアウト処理。
  - JWT（JSON Web Token）等のセッショントークンの発行と検証。
- **関連データストア**:
  - **\[F-1\] ユーザーDB**（ユーザー情報、ハッシュ化パスワード）

#### C. チャット / LLMサービス (Orchestrator)

- **責務**:
  - システムの中核。ユーザーの指示を解釈し、必要な処理をオーケストレーションする。
  - フロントエンドからのチャットメッセージを受信 (WebSocket)。
  - LLM API（例: Gemini）に対し、プロンプト（会話履歴、Function定義）とユーザーメッセージを送信する。
  - LLMの応答（テキストまたはFunction Call要求）を処理する。
- **Function Callingの処理 (重要)**:
  1. LLMからFunction Call要求（例: `calculate_centrality(type='degree')`）を受信。
  2. その要求を\*\*\[D\] 計算サービス\*\*に転送（実行依頼）。
  3. **\[D\] 計算サービス**から計算結果（JSON）を受け取る。
  4. 受け取った結果をLLMに再度送信し、次の行動（2回目のFunction Callまたはテキスト応答）を決定させる。
     - 例: 「次数中心性の計算結果は...です。ユーザーは『大きく表示して』と言っています。」

  5. LLMから2回目のFunction Call要求（例: `map_visual_property(property='node_size', metric='degree_centrality')`）を受信。
  6. その要求を\*\*\[E\] 可視化状態管理サービス\*\*に転送（実行依頼）。
  7. LLMからの最終的なテキスト応答（例: 「次数中心性をノードサイズに割り当てました」）をFEに送信する。
- **関連データストア**:
  - **\[F-2\] プロジェクトDB**（会話履歴の読み書き）

#### D. 計算サービス (Compute Engine)

- **責務**:
  - ネットワーク分析（各種中心性、コミュニティ検出）やレイアウト計算（ForceAtlas2など）の重い処理を実行する。
  - **\[C\] チャット/LLMサービス**からの計算リクエストに応じて動作する。
- **処理フロー (永続化)**:
  1. 計算リクエスト（例: `project_id`の`degree_centrality`）を受信。
  2. **\[F-3\] 計算結果DB**に、該当する計算結果が既に存在するか確認。
  3. **存在する場合**: DBから結果を取得し、即座に返す。
  4. 存在しない場合:

     a. \[F-2\] プロジェクトDBから元のグラフデータをロード。

     b. 指標またはレイアウトを計算 (例: networkx ライブラリ使用)。

     c. 計算結果を\*\*\[F-3\] 計算結果DBに保存（永続化）。

     d. 計算結果を\[C\] チャット/LLMサービス\*\*に返す。
- **入出力**:
  - **入力**: 計算ジョブ定義（例: `{ project_id: '...', calculation: 'degree_centrality' }`）
  - **出力**: 計算結果データ（例: `{ 'node1': 0.5, 'node2': 0.8, ... }`）

#### E. 可視化状態管理サービス (State Manager)

- **責務**:
  - プロジェクトごとの現在の「可視化設定（マッピング状態）」を管理する。
    - 例: `{ node_size: 'degree_centrality', node_color: 'community_id', layout: 'force_atlas_2' }`
  - **\[C\] チャット/LLMサービス**からのマッピング要求（例: `map_visual_property`）に基づき、この状態を更新する。
  - 状態が更新された際、フロントエンド向けの最終的な**描画用JSON**を生成し、フロントエンドにプッシュする（WebSocket経由）。
- **描画JSONの生成プロセス**:
  1. 現在の状態（例: サイズ=`degree`）を把握。
  2. **\[F-2\] プロジェクトDB**から基本データ（ノードリスト、エッジリスト）を取得。
  3. **\[F-3\] 計算結果DB**から必要な計算結果（次数中心性の値、レイアウト座標）を取得。
  - これらをマージし、フロントエンドが直接描画できる形式のJSONを生成する。
     - 例: `nodes: [ { id: 'n1', x: 10, y: 20, size: 8, color: '#FF0000' }, ... ], edges: [ ... ]`
- **入出力**:
  - **入力**: マッピング更新リクエスト（例: `{ node_size: 'degree_centrality' }`）
  - **出力**: フロントエンドへの描画用JSONデータ (WebSocket Push)

#### F. データストア (Databases)

- **F-1. ユーザーDB (例: PostgreSQL, MySQL)**
  - **内容**: ユーザーアカウント情報、認証情報。
  - **アクセス元**: \[B\] 認証サービス
- **F-2. プロジェクトDB (例: MongoDB, DocumentDB)**
  - **内容**: ユーザーがアップロードした元のグラフデータ（ノード、エッジ、属性）、プロジェクト情報、チャットの会話履歴。
  - **アクセス元**: \[D\] 計算サービス (読み取り), \[C\] チャット/LLMサービス (会話履歴)
- **F-3. 計算結果DB (例: Redis, PostgreSQL, MongoDB)**
  - **内容**: 計算済みのネットワーク指標、レイアウト座標。(`project_id`と指標名でキー管理)
  - **アクセス元**: \[D\] 計算サービス (読み書き), \[E\] 可視化状態管理サービス (読み取り)

## 4\. データフローの具体例

**シナリオ: ユーザーが「友達が多い人を可視化して」と入力**

1. **フロントエンド**: ユーザー入力をWebSocketで **[A] API Gateway** に送信。
2. **API Gateway**: 認証チェック後、 **\[C\] チャット/LLMサービス** にメッセージを転送。
3. **\[C\] チャット/LLMサービス**:
   - LLMに「"友達が多い人を可視化して"」と問い合わせる。
   - LLMが応答 \$\\rightarrow\$ `Function Call: calculate_centrality(type='degree')`

4. **\[C\]** が **\[D\] 計算サービス** に「次数中心性」の計算を依頼。
5. **\[D\] 計算サービス**:
   - **\[F-3\] 計算結果DB**をチェック（結果はまだ無い）。
   - **\[F-2\] プロジェクトDB**からグラフデータを取得し、次数中心性を計算。
   - 結果を\*\*\[F-3\] 計算結果DB\*\*に保存。
   - 計算結果（例: `{'n1': 0.5, ...}`）を **\[C\]** に返す。

6. **\[C\] チャット/LLMサービス**:
   - LLMに「計算結果は `{'n1': 0.5, ...}` です。元の指示は『可視化して』です。」と再度問い合わせる。
   - LLMが分析 \$\\rightarrow\$ 「友達が多い（次数中心性が高い）」を「可視化（おそらくサイズ割り当て）」と判断。
   - LLMが応答 \$\\rightarrow\$ `Function Call: map_visual_property(property='node_size', metric='degree_centrality')`

7. **\[C\]** が **\[E\] 可視化状態管理サービス** に「ノードサイズを次数中心性にマッピング」するよう依頼。
8. **\[E\] 可視化状態管理サービス**:
   - 内部の可視化状態を `{ node_size: 'degree_centrality' }` に更新。
   - 描画JSON生成ロジックが発火。
   - **\[F-2\]** (ノードリスト) と **\[F-3\]** (次数中心性の値, 既存のレイアウト座標) からデータを取得・マージ。
   - 最終的な描画JSON（ノードサイズが変更されたもの）を生成し、WebSocketで **フロントエンド** にプッシュする。

9. **フロントエンド**:
   - 新しい描画JSONを受信し、画面のグラフを更新（ノードサイズが変わる）。

10. **\[C\] チャット/LLMサービス**:
    - （ステップ6と並行して）LLMからテキスト応答「次数中心性をノードサイズに割り当てました。」も受け取る。
    - このテキストをWebSocketで **フロントエンド** に送信。

11. **フロントエンド**:
    - チャット欄に「次数中心性をノードサイズに割り当てました。」と表示する。
